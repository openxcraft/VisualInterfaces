# Patterns

Composite patterns assembled from primitives. Each pattern solves a recurring task and inherits the state rules of its parts.

## Classification

- Category: patterns

When to use:

- Composing a screen for a recurring task such as finding, filtering, or editing information.
- Checking a flow for missing steps, exits, or recovery paths.

When to avoid:

- Inventing a one-off arrangement for a task a pattern already covers.

## Elements and components

| Pattern | Purpose | Core elements | Rules |
| --- | --- | --- | --- |
| Primary navigation | Move between top-level sections | Nav list, current indicator, badge | Current section is marked in text or shape, not colour alone |
| Bypass link | Let keyboard users skip repeated navigation | First-focusable link, visible on focus, target landmark or heading | The link is the first focusable element on the page and stays hidden until focused; it moves focus to the target, not just the view — a link that only scrolls while focus stays in the header strands the next tab stops. Label the link for its destination ("Skip to main content", or "Skip to checkout form" where a task, not the page, is the destination); on multi-step flows, offer a task-specific target so later steps skip straight to the form. The target accepts programmatic focus and the focus indicator lands visibly on it |
| Search | Find content by query | Search input, suggestions, results list, clear action | Show recent and suggested queries only where appropriate; results state the query. Typeahead updates on every keystroke with the strongest match keyboard-selectable; each row shows title, type, and one secondary detail so the target is confirmable without opening it; scope filters narrow the global box by project, type, or status when the result set is mixed. Evaluate search health on a cadence: success rate (searches ending in a click or completed action), time-to-result, zero-result rate, top click position, and refinement rate. A rising zero-result or refinement rate points at the vocabulary or scope design, not the ranking; log zero-result queries as free research |
| Filtering and sorting | Narrow a list | Filter controls, active filter tags, sort menu, result count | Result count updates with filters; one action clears all filters. On compact screens, keep a sticky filter control above the results with sort as a separate control, showing the active count on the filter control; expand the most-used facets and collapse the rest, using a bottom sheet for a few facets and a full-screen panel for long facet lists. Let people choose several options before applying, with the apply control showing the live result count, and refresh the list once on apply; facet counts recalculate after each selection and count only items currently obtainable, so a count never promises an empty or unavailable result. Keep applied filters visible as removable chips above the results, and make whole labels tappable at the standard target size. For ranges, pair sliders with typed minimum and maximum inputs or preset ranges; for colour, use swatches rather than text lists. State how selections combine: within one facet, choosing several options widens the result, since any selected option matches; across facets, selections narrow the result, since every chosen facet must match — and where that combination is not obvious, say it plainly near the controls. Where a facet holds many options, add a search field inside the facet so a person can jump to an option instead of scrolling the whole list. Cross-check the search results row |
| Data table | Compare structured rows | Header row, sort controls, pagination or load-more, row actions | Sticky header on long tables; density is a user choice where feasible; bulk selection uses a selection column with a select-all that states its scope; keep loading state per section (grouped headers, expanded rows) rather than whole-table only, and keep expanded-row content aligned with the visible viewport during horizontal scroll; cell-level actions combine one link with one or two adjacent button or link actions; sort state is explicit — an unsorted column shows a neutral indicator distinct from ascending and descending, the current direction is visible in the header and announced to assistive technology, multi-column sort states its column order and uses a unique field as the final tie-breaker so paging stays stable, sorting moves to the server once the set exceeds what the client can sort without lag, and the sort survives paging and filtering; column choice is a user control, not a fixed layout — people can show, hide, and reorder columns to fit the task at hand, and the choice persists across sessions where repeated use is likely; hiding and reordering never rely on drag alone, so keyboard and pointer routes both work; columns can be resized to expose a value in full rather than leaving it truncated |
| Data table density | Fit more rows without losing legibility | Compact, comfortable, and spacious density options; sticky column headers | Density is a per-user choice stored with preferences; row height never drops below the minimum target size |
| Inline editing | Change one value in place inside a table or list | Editable cell, edit trigger, commit and cancel actions, validation message | Keep single-value, low-risk changes inline and move multi-field, cross-field-validated, or high-stakes edits to a dedicated editing surface; an editable cell states that it is editable and names the value it holds; entering edit mode is keyboard-reachable — Enter or a printable key starts editing, Enter commits, Escape cancels and restores the previous value, Tab moves to the next editable field, and arrow keys move between cells while navigating; while editing, navigation keys belong to the control inside the cell, and leaving edit mode returns them to cell navigation; a failed validation keeps the editor open, names the problem in text, and announces it to assistive technology; entering and leaving edit mode is announced, and the confirmed saved value is stated rather than assumed; the visible focus indicator always shows which cell is live |
| Bulk selection | Act on many rows at once | Selection checkboxes, selection count, action bar with the available actions | Selection survives sorting and paging; actions apply to the stated scope and confirm before destructive ones |
| Saved-item collection | Keep items for a later return, grouped by the person | Save action, saved-state indicator, named collections, collection controls, changed-item notice | Save an item with one action from a list or a detail view, and show its saved state wherever the item appears, in text or shape as well as colour. Offer named collections with rename and delete controls, and state the scope of each collection plainly — private or shared — before anything in it is shared. A saved item that the person opens again shows whether it is still current: where the original changed, state what changed or mark the saved copy as stale; where the original was removed, state that plainly and offer removal of the saved copy or the nearest available alternative, never silently dropping or silently swapping it. Unsaving is one action with an undo offer, and the saved view keeps the filtering and sorting controls of the list it came from. Cross-check the filtering and sorting row |
| Bulk action | Apply one decision to many selected items without losing track of scope or failures | Scope statement, action summary, confirmation control, per-item result list, retry and undo controls | State the selection scope before acting — the current page, the filtered set, or all matching items — and never treat a select-all on one page as all matching items unless that is stated and confirmed. A confirmation summarises the action, the count, and the scope, and names any items that will be skipped and why. Destructive batch actions need confirmation; reversible batch actions offer an undo for the whole batch instead of a confirmation for each item. While the batch runs, show progress and keep the selection visible; when it finishes, report successes separately from failures, naming each failed item with its cause and a retry path, and keep failed items selected for that retry. A partial success is never reported as a full success. Cross-check the confirmation row, the bulk selection row, and the undo and trash recovery row |
| Data visualisation | Show trends and comparisons in charts and graphs | Chart, takeaway title, labelled axes and data points, text alternative with a data table | Match the chart type to the story: bars for comparison, lines for change over time, simple types over complex ones; the title states the takeaway, not just the topic; label data directly instead of relying on a legend; never use colour alone — pair it with labels, patterns, or text; every chart carries a text alternative naming the type and the key insight; offer the underlying data as a table; interactive charts are keyboard-operable with a logical tab order; for point-by-point exploration of a plot, offer an explorer mode entered from the plot area, where arrow keys move between neighbouring data points, legend selection, zoom, and search stay reachable by keyboard, and the focused region stays visible when zoomed; the movement geometry follows the chart type — free movement for scatter plots and maps, movement along one axis and within series for line, area, and stacked charts, and movement along the horizontal axis only for waterfall, small-multiple, and grouped-column charts; in right-to-left layouts charts are not mirrored |
| Onboarding | Teach the essential path on first use | Step indicator, one task per step, skip action, progress persistence | Steps focus on what the person must do, not on features; skipping is always allowed and returns later; progress resumes after interruption; detect and prefill language and region with a one-tap correction affordance; never pre-select sensitive fields, and question whether they are needed at all; prefill with the most likely value from location, common choice, or past behaviour; every default stays editable and skips validation until the person changes it; use standard autocomplete tokens so saved values can fill; never set defaults for decisions needing deliberation such as consent or legal acceptance; explain why each field is asked; show one question at a time |
| Guided tour | Point out one element at a time inside the live interface | Dimmed surround, spotlight cut-out, anchored bubble, step counter, back, next, and skip controls | Highlight exactly one element at a time and dim the rest, with a short bubble anchored beside the target stating the benefit in one or two lines, never a paragraph. Show the step position (for example, 2 of 4) and offer back, next, and an always-visible skip or dismiss path; ending the tour early is always allowed and never blocks the task underneath. Use a tour only when a person first reaches a feature or when a change would otherwise disorient them, and prefer inline help or a single tooltip for a lone ambiguous element. Show each tour once per person per feature, never chain more than three steps in sequence, and keep the explained content findable afterwards through help or the element itself. The tour is keyboard-operable and dismissable at any step, and focus returns to a sensible place when it ends. Cross-check the onboarding row |
| Inline assistant actions | Apply automated help to the thing already selected | Contextual command on a selection or row, scope statement, inline preview, undo | Commands appear as verbs on the existing surface — selection menus, row actions, inline toolbars — not as a separate chat surface; inline wins when the target is visible, the task is short, and the result lands where the person already is, while chat wins for open-ended or multi-step exploration; every command states its scope before acting and is reversible, graded by consequence: trivial changes apply with a plain undo, costly ones preview the effect and wait for approval; capabilities are discovered in place, as a suggestion on the selection itself, never through a tour; loading names the running step and error keeps the selection intact |
| Form flow | Collect structured input | Grouped fields, inline validation, summary of errors, submit | Validate on submit and on correction; errors are listed and linked to fields. Decide how each field is collected: ask only for what is genuinely needed; infer what context already tells you and prefill it, always editable; defer non-essential fields to a secondary surface or a later step; confirm with a review step where a mistake has lasting consequences. Smart defaults are for low-risk choices only: a prefilled workspace name removes guesswork, but preselecting recipients or beneficiaries makes a consequential decision for the person — never default what needs deliberation, such as consent, money, or messages sent to others |
| Wizard | Complete a multi-step task | Step indicator, back and next, save and resume | Steps can be revisited; progress is preserved on interruption. Show the total step count up front; mark completed, current, and future steps distinctly, and keep future steps visible but non-interactive — a clickable future step implies a jump the process cannot honour. Step labels are short and specific, never bare numbers; on narrow screens prefer a vertical stepper over a cramped horizontal one. The forward action carries a contextual label where it reduces uncertainty; the back control preserves entered data. Flows longer than a few minutes offer save-and-resume; short simple forms of about five fields with no branching stay on a single page. Scope validation to the visible step: a required field on a hidden step must never block submission silently — either check each step on its own transition, or give each step its own form, so the submit action always reaches a field the person can see and fix |
| Detail view | Inspect one item | Title, key facts, actions, related items | Primary action stays reachable while scrolling on compact screens |
| Notification list | Review updates | Grouped items, read state, mark-all action | Unread state uses shape or text in addition to colour |
| Activity feed | Review a chronological history of events | Event list, timestamp, event-type cue, grouping label, load-more control | Present the feed as a list so assistive technology reports item count and position; grouping that sighted users get from spacing or a connecting line must also be present as structure or text, never as visual grouping alone. Each entry carries a plain timestamp and a type cue in text or shape, not colour alone, so the feed scans without reading every entry. Loading more announces how many entries were added and keeps the person's place — never reload to the top or shift content under the reader. Entries expand in place for detail rather than forcing a jump away, and the whole feed stays keyboard-operable |
| Notification escalation | Match the interruption to the urgency | Urgency scale, badge or dot, toast, banner, notification-centre entry, modal, full-screen dialog | Map urgency to pattern and channel, one step per level: low value goes to a badge or dot in a list; informational goes to a toast or a digest; time-sensitive but non-blocking goes to a persistent banner; action required goes to a notification-centre entry with an email; urgent action required goes to a blocking modal with push and email; critical goes to a full-screen dialog. Nothing critical lives only in a toast — the person may look away and miss it. Never spend a high-urgency pattern on a low-urgency event: it teaches people to ignore alerts, and the ignored-alerts debt then hides the real ones. No redundant multi-channel duplication for the same event; each step up the scale adds disruption, and the scale ends with a channel the person cannot miss |
| Confirmation | Prevent a costly mistake | Plain statement of effect, confirm and cancel actions | Destructive actions name the item and the effect; no pre-selected confirm; grade every action by reversibility: free actions (read-only or trivially reversible) need no interruption, reversible writes get a lightweight inline check with a before-and-after statement, and irreversible actions (pay, send, delete, publish) get the full confirmation ceremony; support standing permissions such as "always draft, never send"; never gate trivial actions or confirmations stop being read |
| Comparison | Choose between options | Option columns or tier cards, criterion rows in a fixed order, difference toggle, decision row | Fix the criterion order across options so rows line up; three to four columns is the workable range; label tiers by audience in plain words, not abstract names; each higher tier opens with "everything in the previous tier, plus…" so readers scan only what is new; a differences-only toggle hides identical rows; mark each row's winner gently with shading plus a text or icon cue, never colour alone; do the arithmetic for the reader ("+$40/month buys 3 extra seats and single sign-on"); state the metric direction explicitly where ambiguous ("lower is better"); keep option labels and a decision row with one action per option sticky on long matrices; spell out annual savings next to the billing toggle; choose the container by difference count — cards when only a few real differences separate the options, tabs or accordions or a grouped collapsible matrix when the feature list is long |
| Permission request | Earn access without losing trust | Pre-permission rationale screen, system dialog, graceful denial path, settings route | Never request on first launch just in case; trigger when the person taps the feature that needs the access; stage one is a custom pre-permission screen stating the concrete value ("to scan receipts and auto-categorise expenses"); if the person taps "not now", do not fire the system dialog; stage two is the system dialog only after a positive pre-prompt response; request one permission at a time — batched prompts produce combined denials; on denial, degrade gracefully into a feature-limited experience, never a dead end; for permanent denial, explain the limitations plainly and route to the app settings; ask once, then only in context; never nag within the same session after a denial; consider a single in-app screen listing all requested permissions with one-tap revocation |
| Install prompt | Offer installation of a web app | Install action, benefit statement, dismiss action, manual-install instructions | Offer installation only after the person has used the app enough to see its value — after a completed task or a return visit — never on first load, never on exit, and never repeatedly after a dismissal; a dismissal stays dismissed, with a quiet persistent route (such as a menu entry) kept instead of re-prompting. State the concrete benefit beside the action (faster access, offline use, notifications) and keep one primary action, not a banner of options. Where the platform offers no prompt event, give manual steps instead of a dead button. After installation, confirm success and hide the prompt; the installed app opens in its own window without browser chrome where supported. Cross-check the permission request row |
| Search results | Recover from finding nothing | Query echo, carried filter chips, ordered recovery actions, facet panel | Keep the division of labour simple: search narrows by intent, filters narrow by attribute; the two controls sit close together since people loop between them; on empty results, say the combination matched nothing and echo it exactly ("no invoices match X with Status: Paid"), keep the query and filters visible, and never silently clear choices; offer recovery in order: a clickable spelling suggestion rather than silent autocorrect, a one-action scope broadening, carried filters as removable chips (an old filter is the most common hidden cause), and a create action where user content is accepted; label each widening action by what it changes; mirror applied filters as chips next to the query echo; a single reset clears filters but leaves the query intact; facet panels sit left on expanded screens and in a bottom sheet on compact ones, with live result counts per facet |
| Command palette | Run commands and jump to content by typing | Summon hint, query input, grouped result list, scope labels, shortcut hints | A complement to menus and buttons, never the only route to a command. Summon with one standard global shortcut; the input takes focus the moment the palette opens. Represent commands as data with verb-led names and match with forgiving subsequence matching plus synonyms, so a query in the user's words finds the right command. Group mixed results into typed sections — navigation, actions, destructive commands — so types stay distinguishable, and never truncate scope information ("Archive project" and "Archive selected files" must read differently after filtering). A blank palette shows recents and common actions; a no-match state explains and offers a next step, never a dead end. Keep selection stable while results stream in: state what happens when the query changes, and never execute whichever row occupies the first position at an uncertain instant. Do not let a broad fuzzy match outrank the clearly intended command when the consequence is costly. Full keyboard operation with a logical order, focus returned to the trigger on close, and result changes announced to assistive technology |
| Offline-first sync | Keep working without a connection | Local store, mutation queue, sync-status area, retry control, freshness indicator | The local store is the source of truth and the server converges later: mutations write to a durable queue with identifiers, timestamps, and attempt counts, and replay when connectivity returns, with a fallback where background sync is unavailable. The interface distinguishes granular states — syncing, local changes pending, stale — instead of a binary loading-versus-done split. Optimistic updates apply at once but stay marked pending until confirmed, then reconcile or roll back on rejection, never failing silently. A visible sync-status area carries the retry control and a manual refresh next to freshness indicators; failed sync gets a non-intrusive banner, never a modal. Derive the shown status from queue progress and real request outcomes, not from a connectivity signal alone: a device can reach a local network while the service itself stays unreachable. Optimistic display is for reversible edits only: where an action has lasting consequences — a booking, a payment, or an access change — keep it marked unconfirmed until the server confirms it, and never clear entered input until the local copy is durable |
| Sync-conflict resolution | Side-by-side version view, field-by-field merge control, merged preview, confirm control | Keep local, keep server, merge fields | When a locally queued change and a newer server version diverge, never silently overwrite either side and never pick a winner by timestamp alone. Show both versions side by side with the differing fields highlighted, and keep the local copy safe until the person resolves the conflict. Where the two sides changed different fields, merge those fields automatically and show the merged result for confirmation; where both sides changed the same field, ask the person to pick one version or edit a merged value. Treat a deletion on one side and an edit on the other as a conflict to resolve, not as a silent delete. Sensitive fields (status, price, assignee, dates) always ask, even when an automatic merge would be possible. The merged preview is the exact result that will be saved, and resolving it records what was chosen so the choice can be reviewed later. Until resolved, the item stays marked as needing attention and the local copy remains recoverable. Cross-check the offline-first sync row |
| Multi-device handoff | Continue a task on another device from an explicit resume point | Resume suggestion on the receiving device, transferred-state summary, fallback view, conflict prompt | Offer the handoff as a one-tap resume suggestion on the receiving device, never as an automatic takeover: the person chooses when to switch. Resume at the exact screen and state where the task stopped — entered input, selection, and scroll position — not merely at the home screen of the receiving app. State plainly what transferred and what did not, so a missing attachment or unsaved draft is visible before work continues. Where the receiving device lacks the app, open the same task in its browser view as a fallback rather than failing silently. Where both devices changed the same item before the switch, resolve it with the sync-conflict rules instead of silently keeping one version. A dismissed suggestion stays dismissed for that task, and a handoff never moves a task away from the device in use without an explicit action. Cross-check the offline-first sync row |
| File upload | Move files in reliably | Per-file queue item, progress indicator, pause, retry, and remove controls | Split large files into chunks of roughly 5–10 MB so a failed chunk retries alone with backoff instead of restarting the whole transfer; use resumable upload where available. Show each queued file as one item with name, progress, status, and error, plus per-file pause, retry, and remove controls; progress stays accurate after interruption and resume. Full keyboard operability with visible focus, and assistive-technology announcements when each file starts, completes, or fails. Where a suitable file is already held, offer it as a one-step reuse choice before asking for a fresh upload: name the file and where it came from, let the person confirm it or decline and upload a different file instead, and never reuse a held file silently. Where the held file no longer meets the requirements — format or recency — say so plainly and ask for a new one rather than failing after the fact. State the accepted formats, size limit, and file-count limit in plain text beside the control before anyone chooses a file, and check a file against those limits before the upload starts, naming the exact limit broken — never let a rejection be the first time the person learns the rule. Drag-and-drop is an enhancement only: a visible, keyboard-operable browse control always offers the same upload, so dragging is never the only path |
| Paywall and upgrade prompt | Explain a limit and an option | Limit statement, option summary, trial offer statement, trial timeline, plan comparison, dismiss action | Dismiss is always present and equally easy to find. The offer states explicitly whether a trial is included, its length, the price that follows, and the first charge date — never leave trial inclusion ambiguous. A control that adds or removes a trial is never the same control that confirms purchase: trial choice and purchase confirmation are separate explicit steps, so changing the trial cannot silently commit the person to an auto-renewing charge. While a trial runs, show its timeline — remaining time, what happens at its end, and a reminder before the first charge — with the cancellation path reachable before that charge. Cross-check the subscription cancellation row. Where options differ, compare them side by side on the same screen with the same price units and the total for the billing period, so the person can tell what each option includes without leaving the screen |
| Subscription cancellation | End a recurring plan without friction | Cancel action, effect statement, pause or plan-change alternatives, written confirmation, resume path | Cancel in the same channel used to sign up, labelled plainly and reachable from the billing or account area without extra menus; the flow states what ends, when access ends, what happens to saved content, and the next billing date before confirmation. Pause or a cheaper plan may be offered beside cancellation, never as a gate to reaching it, and confirmation options use plain parallel wording with no guilt-framed copy. After cancelling, confirm in writing the end date, that billing stops, and how to resume; keep the resume path visible until access ends. Never require a slower channel, such as a call, when sign-up was self-serve |
| Session-expiry warning | Keep work safe when a session ends | Time-remaining warning, keep-working action, sign-out action, saved-draft restore step | Warn before the session ends with the time remaining stated plainly, in a warning that stays visible, never blocks continued work, and is announced to assistive technology; a simple keep-working action extends the session without losing entered input, and an idle limit is stated separately from an absolute limit that activity cannot extend. Never discard a draft or a form on expiry: save entered input first, and on return bring the person back to the same place with the same input, or to a saved draft with a clear restore step. Re-authentication after expiry restores the saved input rather than starting the task again; cross-checked against the draft autosave row and the timeout rules in catalog/states.md |
| Data export | Take a copy of personal data elsewhere | Scope and format choice, includes and excludes statement, progress indicator, download link, partial-failure report | Offer export in common formats the person can actually open elsewhere, and state plainly before starting what the export includes and excludes, including date range, scope, and any records left out. Show real progress for large exports with named stages and a stated download-link lifetime, and let the person leave without cancelling the export where the export runs in the background, with a way to check its status. On a partial failure, name what exported and what did not and offer a retry for the missing part only, never a silent short file; cross-checked against the file upload row |
| Account deletion | Close an account with no surprises | Effect statement, grace-period undo action, export offer, written confirmation | Delete from the same channel used to sign up, labelled plainly and reachable from the account area. Before confirmation, state the effect in plain words: what content is removed, what content kept for other people stays, what records are kept and why, and when removal completes. Offer an export of personal data before deletion starts. After the request, sign the person out everywhere, and during a stated grace period offer a plain undo path that restores the account whole; once removal completes, confirm it in writing. Never require a slower channel, and never present deletion as instant when a grace period or a backup-retention window still applies; cross-checked against the subscription cancellation row and the confirmation row |
| Account switcher | Move between signed-in accounts without losing the current place | Current-account trigger, signed-in account list, active-account mark, add-account action, per-account sign-out action | The trigger always names the active account in text, not by an image alone, and the list marks the active account in text as well as in shape. Switching keeps the person in the same place wherever that place exists for the new account, and falls back to that account's home view where it does not. Data, drafts, and settings never carry across a switch unless the person explicitly moves them. Signed-in accounts stay signed in after a switch, and signing out of one account never signs out of the others unless that is chosen explicitly. An add-account action stays in the same list, and a switch never asks for credentials for an account that is already signed in |
| In-product help | Get help without leaving the task | Persistent help entry, context-aware suggestions, in-place search, escalation path, article feedback | Keep one help entry reachable from every screen, labelled the same everywhere, so help is found at the moment of confusion rather than after leaving the task. Suggestions follow the current screen and task, not a generic list: a person on a billing screen sees billing help first. Search runs inside the product and results open in place without losing entered input, and returning from help restores the exact screen and state. Each article answers first in short sentences, covers one task, and lists what to try when the first fix fails. When search finds nothing, offer escalation that carries the current screen and task context to the human path, never a dead end and never a blank search page. Every article carries a simple helpful-or-not control, and repeated negative feedback marks the article for rewrite. Help panels are dismissible, keyboard-operable, and announced to assistive technology without stealing focus from the task |
| Share link | Let someone else open the same item | Link field, copy action, access-scope statement, expiry statement, revoke control | State the access scope and the expiry before sharing: named people versus anyone with the link, and when access ends. Default to named access where the item is sensitive; an anyone-link is an explicit choice, not the default. The copy action confirms in place with a visible change and an announcement to assistive technology, then returns to its copy state so it can be used again. When copying fails, select the link text and offer a manual copy path instead of failing silently, and never let a slow network round trip consume the copy gesture before the link is ready — prepare the link first, then copy on the tap. A shared link opens at the same item and state; an expired or revoked link explains why it no longer opens and offers a request-access path. Where access is named, the owner can see who holds it and revoke it in one step |
| Second-factor sign-in | Confirm identity with a second step without locking people out | Code entry, method choice, resend control, backup-code entry, trusted-device choice | Offer the strongest available method first and list every method plainly, so the person chooses with full information rather than accepting a weak default. Code entry accepts pasted codes in full and moves focus sensibly, never breaking a paste across separate boxes. A resend control shows the wait time and states where the code was sent. A wrong code states how many attempts remain without revealing which part failed, and never locks the account on a single mistake. A backup-code path stays visible at all times, not hidden behind failed attempts: each backup code works once, and generating a new set cancels the old set. Saving backup codes is part of setup, not an afterthought — show them once, ask the person to store them somewhere safe and separate from the device, and confirm they were saved before finishing. A trusted-device choice is opt-in per device with a stated duration, and is never offered by default on a shared device. A second factor counts as enabled only after a code from it verifies successfully |
| Consent choice | Record a preference | Plain description, accept and decline, link to detail | Decline is as prominent as accept; choice is changeable later |
| Granular consent | Give informed control over data use | Per-category toggles, just-in-time disclosure, consent history, revoke control | Consent is never one pre-checked box: list categories as separate toggles (required, functional, analytics, marketing) with one-sentence consequences each, and never pre-check an optional one — silence is not agreement. Disclose at the point of need: ask when the data is about to be used, with the specific purpose named, not months earlier in a blanket policy. Revocation is frictionless: one control, immediate effect, no retention of withdrawn consent, and the choice stays changeable from settings. Keep an audit trail of each decision with its time and scope, so the person can review and correct it. Cross-check the consent signals in trends/2026/machine-experience.md — high-risk automated actions always pause for human confirmation |
| Media viewer | Inspect visual content | Stage, previous and next, caption, close | Keyboard and swipe both work; captions are text, not embedded in the visual |
| Simplified view | Reduce cognitive load on demand | Simplified-mode toggle, reading view, critical-region markers | Offer a simplified version that hides non-essential features and shortens text; keep it available, easy to enter, and easy to leave; mark content on critical paths for simplification (data-simplification attribute) so personalization tools can reduce it; extra features stay discoverable when wanted, never permanently removed |
| Map comparison | Compare places and changes on a map | Map canvas, markers, info pop-up or panel, layer control | Short hover notes on features avoid opening a full detail view; visited markers show which pop-ups were already opened so people stop reopening them; small multiples — same-size, same-scale maps side by side — beat toggled layers for comparing change over time; a peel-back swipe temporarily reveals the layer underneath for overlap comparison; short detail goes in a pop-up, long or interactive content in an info panel that never covers the map itself; rich markers add a key metric where colour or size alone cannot carry the information; dragging is never the only way to pan, place a stop, or reorder a route — offer directional pan controls, a tap-to-place action, an address entry field, and reorder controls, plus arrow-key panning; a documented exit returns focus to the list or the next control, and zoom, locate, and close controls carry accessible names rather than icon-only labels |
| Location selection | Choose a place from a map and list | Area search, current-location action, map canvas, result list, detail card, confirm control | Start with an area search and offer a current-location action only as a choice, asking for location access when that action is chosen. Map and list show the same places, and a selection stays identifiable in both when the map moves. Detail cards carry what decides the choice — name, address, hours, and availability — since proximity alone cannot answer it. Refreshing the area happens on request, never silently on every pan, so a selection is never lost to a redraw. When no place meets the current requirements, keep the searched area, explain what failed, and offer a changed area or a removed filter. | Find-in-page | Search within the current long page or document | Query field, match count, next and previous controls, match highlights, dismiss control | Keep the query persistent while stepping through matches; show the match position as a count (for example, 3 of 12) and move focus to the matched text, scrolling it into view below any sticky header. Highlight every match, with the current match distinct in shape as well as colour. Next and previous wrap or state the end plainly; a query with no matches says so in place and offers to clear or widen the query rather than a dead end. Dismissing returns to the previous place with highlights cleared. Where the content spans pages or unloaded sections, state the search scope plainly — searching only loaded content must never look like searching everything. Distinct from the search row, which finds content across the product rather than within the current page. Cross-check the search row and the long-document navigation row |
| Collaborative editing presence | Show who else is present in a shared document and which part each person is editing, without letting two people overwrite the same field unknowingly | Presence list, field highlight, field hold indicator, editing-mode cue | Show who is present in the document with a presence list that names each person in text as well as in colour, and mark the field each person is editing with a visible hold so a second editor sees it before typing. A held field is not a hard block: where two edits would collide, warn before overwriting and offer the sync-conflict rules instead of silently keeping one version. Presence is a short-lived claim about an open session, never proof that a person saw, understood, or approved a change: keep read and approval signals separate from presence, and drop a presence mark promptly when the session ends or goes idle. Show typing or selection cues only for the field in view, so presence never distracts from the text being read. Cross-check the sync-conflict resolution row and the annotation and comment thread row |
| Draft autosave and recovery | Keep unfinished work safe across interruption, and restore it with a clear review step | Saved indicator, draft restore prompt, discard control, draft list | Save drafts continuously with a visible saved indicator that states when the draft was last saved, so a person never wonders whether work is safe. After a crash, a closed tab, or an interrupted session, restore the latest draft with a clear review step: show what was restored and let the person keep it, edit it, or discard it — never restore silently over newer work. A restored draft is not a sent message or a saved record: keep draft and delivery states separate, and clear the draft once the work is submitted or explicitly discarded. Offer an explicit discard path, and state the draft's scope plainly — this device only, or across devices — and how long it is kept. Cross-check the wizard save-and-resume rules and the session-expiry warning row |
| Saved-filter view | Return to a filter combination in one action, without rebuilding it on each visit | Saved-view list, save-view control, rename and delete controls, stale-view marker | A named view stores a filter combination — filters, sort order, and column choices — for one-tap return, and saves the definition rather than a frozen result, so the view stays current as data changes. Offer rename and delete controls for every saved view, and state its scope plainly — private or shared — before anyone else can see it. When a saved view no longer matches the current data — because a filter value was removed or renamed — mark it visibly and offer a repair step rather than silently showing a different result. Keep the query text out of a saved view unless the person chose to include it, and keep a saved view distinct from a single saved item: a view re-runs its filters, a saved item returns one chosen thing. Cross-check the filtering and sorting row and the saved-item collection row |

## Layout and responsive rules

- One pattern owns the primary action of a screen; supporting patterns stay visually quieter.
- On compact screens, patterns stack in task order: search, filters, results, actions.
- On expanded screens, filters may sit beside results; the result count stays with the results.
- Keep the path back: every pattern that opens a detail or a step offers a clear return.
- Do not nest dialogs; use a new view when a second layer of decisions appears.

## States

Every element and page in this group defines all seven states. Missing states are treated as incomplete work.

| State | Appearance | Behaviour |
| --- | --- | --- |
| Default | A pattern at rest, with full contrast and a clear label. | Ready for input or selection. |
| Hover | Pointer-only highlight: subtle background or border change. | No change on touch devices; hover never carries essential information alone. |
| Active | Pressed or selected appearance while interaction is in progress. | Feedback appears within 100 ms of input. |
| Disabled | Reduced contrast, no pointer response, still readable. | Explain why it is unavailable nearby when the reason is not obvious. |
| Loading | Skeleton blocks or a progress indicator replace live content. | Keep layout dimensions stable so content does not shift. |
| Empty | State why the area is empty and offer the action that fills it, or a reset when filters cause it. | Offer one clear next action and, where relevant, a reset for filters. |
| Error | Keep the pattern's structure, show the failure in place, and offer retry without losing input. | Keep entered data, place the message next to the problem, and offer a retry. |
