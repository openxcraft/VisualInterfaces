# Patterns

Composite patterns assembled from primitives. Each pattern solves a recurring task and inherits the state rules of its parts.

## Classification

- Category: patterns

When to use:

- Composing a screen for a recurring task such as finding, filtering, or editing information.
- Checking a flow for missing steps, exits, or recovery paths.

When to avoid:

- Inventing a one-off arrangement for a task a pattern already covers.

## Elements and components

| Pattern | Purpose | Core elements | Rules |
| --- | --- | --- | --- |
| Primary navigation | Move between top-level sections | Nav list, current indicator, badge | Current section is marked in text or shape, not colour alone |
| Bypass link | Let keyboard users skip repeated navigation | First-focusable link, visible on focus, target landmark or heading | The link is the first focusable element on the page and stays hidden until focused; it moves focus to the target, not just the view — a link that only scrolls while focus stays in the header strands the next tab stops. Label the link for its destination ("Skip to main content", or "Skip to checkout form" where a task, not the page, is the destination); on multi-step flows, offer a task-specific target so later steps skip straight to the form. The target accepts programmatic focus and the focus indicator lands visibly on it |
| Back to top | Return to the top of a long page without scrolling back by hand | Floating button, scroll-distance threshold, top landmark or heading | Offer it only where the page is long enough that scrolling back is a chore, roughly more than two screens of content; on short pages omit it rather than showing a control that never helps. Keep it hidden while the person is near the top and show it only after they have scrolled past a stated distance, hiding it again when they return near the top, so it never sits on content that needs no scrolling. Fix it where it is easy to reach without covering content or other floating controls, commonly the bottom-right corner, clear of chat widgets, banners, and the primary action, and keep it at the standard touch-target size. On activation, scroll to the top and move keyboard focus to the top landmark or heading, not just the view, so the next tab stops follow from the top; label the control for its destination rather than a bare symbol. Scroll smoothly, but honour reduced-motion settings by jumping at once. Distinct from the Reading progress indicator row, which shows how far through reading the person has come without moving them, and from the long-document navigation row, which moves within a document rather than back to its start. Cross-check the Reading progress indicator row |
| Search | Find content by query | Search input, suggestions, results list, clear action | Show recent and suggested queries only where appropriate; results state the query. Typeahead updates on every keystroke with the strongest match keyboard-selectable; each row shows title, type, and one secondary detail so the target is confirmable without opening it; scope filters narrow the global box by project, type, or status when the result set is mixed. Keep the suggestion panel to a small scannable set, grouped and labelled where more than one content type returns, so the list stays readable at a glance; Escape closes the panel before it clears the query, and Enter commits the query as typed. Evaluate search health on a cadence: success rate (searches ending in a click or completed action), time-to-result, zero-result rate, top click position, and refinement rate. A rising zero-result or refinement rate points at the vocabulary or scope design, not the ranking; log zero-result queries as free research. Keep recent queries in their own labelled group, separate from completions and suggestions, so a past query is never mistaken for a recommendation. Each recent entry offers its own removal and the group offers a clear-all, since a history the person cannot prune becomes a record they did not choose. Show only queries that were actually run, newest first, and state plainly whether recents live on this device only or follow sign-in, clearing on sign-out on shared devices unless the person chose otherwise. Highlight the matched substring inside each suggestion so the match is scannable at a glance, and while new suggestions load, keep the previous rows on screen and swap them in one change so the panel never flashes empty. Where a suggestion is offered as a refinement rather than a result, let its refinement control append the suggestion to the query without running the search, so the query can be built up step by step; keep that control distinct from the row itself, which runs the search. |
| Search history | Return to a query already run, change it, or remove it | History list, re-run control, edit control, per-item delete, clear-all control, retention statement | Keep only queries that were actually run, newest first, each entry naming the query and when it was run. A re-run control runs the same query again at once, while an edit control loads the query into the search box without running it, so it can be changed first. Offer a delete control on each entry and a clear-all control for the whole list, and state plainly how long entries are kept and whether they live on this device only or follow sign-in, clearing on sign-out on shared devices unless the person chose otherwise. Keep history in its own labelled list, never mixed with suggestions or recommendations, so a past query is never mistaken for a suggestion. Distinct from the recently viewed row, which lists opened items rather than queries, and from the saved-filter view row, which keeps a named filter combination rather than past queries. Cross-check the search row and the recently viewed row |
| Filtering and sorting | Narrow a list | Filter controls, active filter tags, sort menu, result count | Result count updates with filters; one action clears all filters. On compact screens, keep a sticky filter control above the results with sort as a separate control, showing the active count on the filter control; expand the most-used facets and collapse the rest, using a bottom sheet for a few facets and a full-screen panel for long facet lists. Let people choose several options before applying, with the apply control showing the live result count, and refresh the list once on apply; facet counts recalculate after each selection and count only items currently obtainable, so a count never promises an empty or unavailable result. Keep applied filters visible as removable chips above the results, and make whole labels tappable at the standard target size. For ranges, pair sliders with typed minimum and maximum inputs or preset ranges; for colour, use swatches rather than text lists. State how selections combine: within one facet, choosing several options widens the result, since any selected option matches; across facets, selections narrow the result, since every chosen facet must match — and where that combination is not obvious, say it plainly near the controls. Where a facet holds many options, add a search field inside the facet so a person can jump to an option instead of scrolling the whole list. For assistive technology, group each facet's options under a named group so the group is announced with its options; name each applied-filter chip's remove control for the filter it removes rather than a bare symbol, and announce the new result count as a status message when filters change, without moving focus. Cross-check the search results row |
| Data table | Compare structured rows | Header row, sort controls, pagination or load-more, row actions | Sticky header on long tables; density is a user choice where feasible; bulk selection uses a selection column with a select-all that states its scope; keep loading state per section (grouped headers, expanded rows) rather than whole-table only, and keep expanded-row content aligned with the visible viewport during horizontal scroll; cell-level actions combine one link with one or two adjacent button or link actions; sort state is explicit — an unsorted column shows a neutral indicator distinct from ascending and descending, the current direction is visible in the header and announced to assistive technology, multi-column sort states its column order and uses a unique field as the final tie-breaker so paging stays stable, sorting moves to the server once the set exceeds what the client can sort without lag, and the sort survives paging and filtering; column choice is a user control, not a fixed layout — people can show, hide, and reorder columns to fit the task at hand, and the choice persists across sessions where repeated use is likely; hiding and reordering never rely on drag alone, so keyboard and pointer routes both work; columns can be resized to expose a value in full rather than leaving it truncated |
| Data table density | Fit more rows without losing legibility | Compact, comfortable, and spacious density options; sticky column headers | Density is a per-user choice stored with preferences; row height never drops below the minimum target size |
| Expandable table row | Reveal detail for one row without leaving the table | Row toggle, detail row, collapse control | Each row that holds more detail offers a named toggle in its first cell stating expand or collapse in text as well as in shape, and expanding never moves focus away from the toggle; short detail appears in a detail row directly beneath its parent row spanning the full table width, while long detail opens as a separate detail view so the table stays scannable; only rows with detail carry a toggle, and a toggle never acts as the row's only action; the expanded state is announced to assistive technology and the detail content stays in reading order after its parent row; expand-all and collapse-all controls appear only where every row holds detail, and collapsing a row never discards entered input inside its detail — distinct from the accordion disclosure row, which organises sections under headings, and from the detail view row, which inspects one item without a sibling table. |
| Inline editing | Change one value in place inside a table or list | Editable cell, edit trigger, commit and cancel actions, validation message | Keep single-value, low-risk changes inline and move multi-field, cross-field-validated, or high-stakes edits to a dedicated editing surface; an editable cell states that it is editable and names the value it holds; entering edit mode is keyboard-reachable — Enter or a printable key starts editing, Enter commits, Escape cancels and restores the previous value, Tab moves to the next editable field, and arrow keys move between cells while navigating; while editing, navigation keys belong to the control inside the cell, and leaving edit mode returns them to cell navigation; a failed validation keeps the editor open, names the problem in text, and announces it to assistive technology; entering and leaving edit mode is announced, and the confirmed saved value is stated rather than assumed; the visible focus indicator always shows which cell is live |
| Bulk selection | Act on many rows at once | Selection checkboxes, selection count, action bar with the available actions | Selection survives sorting and paging; actions apply to the stated scope and confirm before destructive ones |
| Saved-item collection | Keep items for a later return, grouped by the person | Save action, saved-state indicator, named collections, collection controls, changed-item notice | Save an item with one action from a list or a detail view, and show its saved state wherever the item appears, in text or shape as well as colour. Offer named collections with rename and delete controls, and state the scope of each collection plainly — private or shared — before anything in it is shared. A saved item that the person opens again shows whether it is still current: where the original changed, state what changed or mark the saved copy as stale; where the original was removed, state that plainly and offer removal of the saved copy or the nearest available alternative, never silently dropping or silently swapping it. Unsaving is one action with an undo offer, and the saved view keeps the filtering and sorting controls of the list it came from. Cross-check the filtering and sorting row |
| Saved collection sharing | Share a saved collection with another person while keeping control of access | Share control, recipient choice, access-level choice, shared-collection list, revoke control, access-change notice | State the scope before sharing: whether the share covers the whole collection including items added later, or only the items in it now, so a new item is never shared by surprise. Offer two access levels in plain words: view-only, which lets the recipient see the collection without adding, removing, or renaming anything in it, and editable, which lets the recipient add and remove items but never change who else can see the collection — only the owner changes sharing. Where a link route is offered, state plainly whether anyone with the link can view the collection or only named recipients, and whether opening it needs sign-in, since a link passed on reaches people beyond the named recipients. Keep a shared-collection list where the owner reviews every recipient and access level, and offer a revoke control on each recipient that takes effect at once. State before sharing, and again at revoke time, what happens to items the revoked person added: they stay in the collection or leave with that person, never silently either way, and a copy a recipient made stays with the recipient after revocation. When the owner narrows a shared collection back to private, state that every recipient loses access at once and that the collection itself stays with the owner. Distinct from the saved-item collection row, which keeps items for one person, and from the shared cart row, which shares items for a single checkout. Cross-check the saved-item collection row and the shared cart row |
| Bulk action | Apply one decision to many selected items without losing track of scope or failures | Scope statement, action summary, confirmation control, per-item result list, retry and undo controls | State the selection scope before acting — the current page, the filtered set, or all matching items — and never treat a select-all on one page as all matching items unless that is stated and confirmed. A confirmation summarises the action, the count, and the scope, and names any items that will be skipped and why. Destructive batch actions need confirmation; reversible batch actions offer an undo for the whole batch instead of a confirmation for each item. While the batch runs, show progress and keep the selection visible; when it finishes, report successes separately from failures, naming each failed item with its cause and a retry path, and keep failed items selected for that retry. A partial success is never reported as a full success. Cross-check the confirmation row, the bulk selection row, and the undo and trash recovery row |
| Data visualisation | Show trends and comparisons in charts and graphs | Chart, takeaway title, labelled axes and data points, text alternative with a data table | Match the chart type to the story: bars for comparison, lines for change over time, simple types over complex ones; the title states the takeaway, not just the topic; label data directly instead of relying on a legend; never use colour alone — pair it with labels, patterns, or text; every chart carries a text alternative naming the type and the key insight; offer the underlying data as a table; never leave a key value only in a tooltip — a value that matters belongs on the chart or in the data table, since a hover-only value is unreachable by keyboard and touch; interactive charts are keyboard-operable with a logical tab order; for point-by-point exploration of a plot, offer an explorer mode entered from the plot area, where arrow keys move between neighbouring data points, legend selection, zoom, and search stay reachable by keyboard, and the focused region stays visible when zoomed; the movement geometry follows the chart type — free movement for scatter plots and maps, movement along one axis and within series for line, area, and stacked charts, and movement along the horizontal axis only for waterfall, small-multiple, and grouped-column charts; in right-to-left layouts charts are not mirrored; where an audio rendering is offered, it complements rather than replaces the text alternative and the data table, maps rising values to rising pitch so a trend can be heard, announces each value as it plays, and stays under the person's control with pause and stop, never starting on its own |
| Onboarding | Teach the essential path on first use | Step indicator, one task per step, skip action, progress persistence | Steps focus on what the person must do, not on features; skipping is always allowed and returns later; progress resumes after interruption; detect and prefill language and region with a one-tap correction affordance; never pre-select sensitive fields, and question whether they are needed at all; prefill with the most likely value from location, common choice, or past behaviour; every default stays editable and skips validation until the person changes it; use standard autocomplete tokens so saved values can fill; never set defaults for decisions needing deliberation such as consent or legal acceptance; explain why each field is asked; show one question at a time |
| Guided tour | Point out one element at a time inside the live interface | Dimmed surround, spotlight cut-out, anchored bubble, step counter, back, next, and skip controls | Highlight exactly one element at a time and dim the rest, with a short bubble anchored beside the target stating the benefit in one or two lines, never a paragraph. Show the step position (for example, 2 of 4) and offer back, next, and an always-visible skip or dismiss path; ending the tour early is always allowed and never blocks the task underneath. Use a tour only when a person first reaches a feature or when a change would otherwise disorient them, and prefer inline help or a single tooltip for a lone ambiguous element. Show each tour once per person per feature, never chain more than three steps in sequence, and keep the explained content findable afterwards through help or the element itself. The tour is keyboard-operable and dismissable at any step, and focus returns to a sensible place when it ends. Cross-check the onboarding row |
| Setup checklist | Track multi-step setup that can be left and returned to | Ordered task list, per-task state, resume control, skip control, progress count | List the setup tasks in order, each with a done, current, or remaining state stated in text as well as in shape, and show the count done of the total so progress is plain at a glance. Each item links directly to the task it names, so completing it happens in place rather than reading about it; items map to outcomes, not to a tour of features, and the list stays short — a handful of tasks toward one activation goal. A person can leave at any point and return later: a resume control takes them to the first unfinished task, and progress persists across sessions. Any item can be skipped, and skipped items stay reachable rather than vanishing, until the person dismisses them deliberately; dismissing the whole list never blocks the task underneath, and a finished list is marked complete rather than left dangling. Use a checklist where setup spans several separate actions; where there is only one thing to do, a single prompt replaces it. Cross-check the onboarding row and the guided tour row |
| Inline assistant actions | Apply automated help to the thing already selected | Contextual command on a selection or row, scope statement, inline preview, undo | Commands appear as verbs on the existing surface — selection menus, row actions, inline toolbars — not as a separate chat surface; inline wins when the target is visible, the task is short, and the result lands where the person already is, while chat wins for open-ended or multi-step exploration; every command states its scope before acting and is reversible, graded by consequence: trivial changes apply with a plain undo, costly ones preview the effect and wait for approval; capabilities are discovered in place, as a suggestion on the selection itself, never through a tour; loading names the running step and error keeps the selection intact |
| Form flow | Collect structured input | Grouped fields, inline validation, summary of errors, submit | Validate on submit and on correction; errors are listed and linked to fields. Do not validate while the person is still typing: check a field once on leaving it, then re-check on each change after it has been marked invalid, so the error clears as soon as the value is corrected. Keep each inline message beside its field, in text with an icon or label rather than colour alone, stating what is wrong and what fixes it. On submit failure, move focus to a summary at the top stating the count, with each entry linking to and focusing its field, while keeping the inline messages in place — the summary alone is never the only indication, and a failure is never announced only through a disappearing notice. Decide how each field is collected: ask only for what is genuinely needed; infer what context already tells you and prefill it, always editable; defer non-essential fields to a secondary surface or a later step; confirm with a review step where a mistake has lasting consequences. Smart defaults are for low-risk choices only: a prefilled workspace name removes guesswork, but preselecting recipients or beneficiaries makes a consequential decision for the person — never default what needs deliberation, such as consent, money, or messages sent to others. Never move focus automatically to a field when the form loads: let the person choose where to start, since an unexpected focus jump disorients keyboard and screen-reader users. Where a control is non-standard, or a required field cannot be filled in from stored information, put a short explanation and a worked example beside the control itself, not only in help: state what the control does, show what a valid entry looks like, and keep that explanation reachable without leaving the field |
| Character count | Show how much text a limited field still accepts | Limit statement, count indicator, over-limit message | State the limit before typing starts, in words beside the field, never only as a silent cutoff: "up to 200 characters" beats a bare number. Show the count as characters used or remaining, updated as the person types, placed where it stays visible without covering the input, and keep it in text rather than colour alone. Announce the count to assistive technology on entry and at meaningful thresholds, not on every keystroke, and state plainly when the limit is reached or exceeded, including how many characters over the limit the text is. Never silently discard typed or pasted text beyond the limit: either stop entry with a plain statement, or accept the excess and mark the field invalid with a clear path to shorten it. Cross-check the Form flow row |
| Wizard | Complete a multi-step task | Step indicator, back and next, save and resume | Steps can be revisited; progress is preserved on interruption. Show the total step count up front; mark completed, current, and future steps distinctly, and keep future steps visible but non-interactive — a clickable future step implies a jump the process cannot honour. Step labels are short and specific, never bare numbers; on narrow screens prefer a vertical stepper over a cramped horizontal one. The forward action carries a contextual label where it reduces uncertainty; the back control preserves entered data. Flows longer than a few minutes offer save-and-resume; short simple forms of about five fields with no branching stay on a single page. Scope validation to the visible step: a required field on a hidden step must never block submission silently — either check each step on its own transition, or give each step its own form, so the submit action always reaches a field the person can see and fix. Mark the current step for assistive technology as well as in sight: the step list names the current step as the current step and states its position, such as step two of five, and announces the new step when the person moves to it, so a step list never reads as a row of identical labels; completed steps are named as completed in text, never by a check mark alone |
| Detail view | Inspect one item | Title, key facts, actions, related items | Primary action stays reachable while scrolling on compact screens |
| Notification list | Review updates | Grouped items, read state, mark-all action, snooze and pause controls | Unread state uses shape or text in addition to colour. Offer a snooze on individual items and a pause for the whole list: a snoozed item leaves the list and returns at the chosen time as unread, never silently dropped, and the snooze choice states its return time in plain words rather than a vague interval. A pause states when it ends and what still breaks through, so time-sensitive items are never paused away unseen; when the pause ends, held items arrive together as a grouped summary, not as a flood of separate interruptions. Snoozing one item never silences the rest, and clearing a snoozed item cancels its return. Cross-check the notification digest and notification escalation rows |
| Notification preferences | Choose which updates arrive, through which channel, and how often | Category groups, channel matrix, cadence control, quiet-hours control, per-source mute, reset control | Group settings by the topics the person cares about — messages, mentions, billing, activity — rather than by internal event names, and let each group be switched independently so turning one topic off never silences everything. Lay categories against channels in one matrix, so a person can choose one channel for billing and another for mentions at a glance, with the on-or-off state unmistakable in text or shape as well as colour. Offer a cadence per category — at once, as a scheduled summary, or off — and never let a summary be the only place an action-required item appears. Offer quiet hours that state plainly when they end and which urgent items still break through, and a per-source mute that silences one noisy source without touching the rest. Start quiet for promotional updates and let the person opt into more, and keep a single reset that returns every preference to its starting value. Apply a change at once and keep it saved across visits, and state plainly where a choice is governed by a system-level permission rather than this screen, so a switch that cannot take effect never looks as if it did. Cross-check the notification list row, the notification digest row, and the notification escalation row |
| Activity feed | Review a chronological history of events | Event list, timestamp, event-type cue, grouping label, load-more control, new-items control | Present the feed as a list so assistive technology reports item count and position; grouping that sighted users get from spacing or a connecting line must also be present as structure or text, never as visual grouping alone. Each entry carries a plain timestamp and a type cue in text or shape, not colour alone, so the feed scans without reading every entry. Loading more announces how many entries were added and keeps the person's place — never reload to the top or shift content under the reader. When new entries arrive while the feed is being read, hold them behind a count control rather than inserting them at the top and shifting content under the reader; activating the control adds the new entries at the top, announces how many were added, and keeps the reader's place. Show a relative timestamp on each entry with the exact time available on demand, and use a connecting line only where order and elapsed time carry meaning — otherwise a plain divider separates entries without implying a sequence. Entries expand in place for detail rather than forcing a jump away, and the whole feed stays keyboard-operable |
| Notification escalation | Match the interruption to the urgency | Urgency scale, badge or dot, toast, banner, notification-centre entry, modal, full-screen dialog | Map urgency to pattern and channel, one step per level: low value goes to a badge or dot in a list; informational goes to a toast or a digest; time-sensitive but non-blocking goes to a persistent banner; action required goes to a notification-centre entry with an email; urgent action required goes to a blocking modal with push and email; critical goes to a full-screen dialog. Nothing critical lives only in a toast — the person may look away and miss it. Never spend a high-urgency pattern on a low-urgency event: it teaches people to ignore alerts, and the ignored-alerts debt then hides the real ones. No redundant multi-channel duplication for the same event; each step up the scale adds disruption, and the scale ends with a channel the person cannot miss |
| Confirmation | Prevent a costly mistake | Plain statement of effect, confirm and cancel actions | Destructive actions name the item and the effect; no pre-selected confirm; grade every action by reversibility: free actions (read-only or trivially reversible) need no interruption, reversible writes get a lightweight inline check with a before-and-after statement, and irreversible actions (pay, send, delete, publish) get the full confirmation ceremony; support standing permissions such as "always draft, never send"; never gate trivial actions or confirmations stop being read |
| Sensitive-action re-confirmation | Check intent again before a consequential change that an old sign-in must not silently approve | Fresh confirmation step, plain statement of what will change, scope statement, cancel action | Before a consequential action such as changing payment details, sharing sensitive content, or deleting shared content, ask for a fresh confirmation tied to that action itself: state plainly what will change, for whom, and whether it can be undone. Never reuse an earlier sign-in as silent approval for a new consequential action, and never pre-select the confirm control. Grade the check to the consequence — a plain restatement for a reversible change, a fresh credential or typed confirmation for an irreversible one — and keep the cancel action as easy to reach as the confirm action. A declined re-confirmation leaves everything exactly as it was, with no partial change applied. Distinct from the second-factor sign-in row, which adds a check at sign-in, and from the confirmation row, which confirms an ordinary action. Cross-check the confirmation row |
| Comparison | Choose between options | Option columns or tier cards, criterion rows in a fixed order, difference toggle, decision row | Fix the criterion order across options so rows line up; three to four columns is the workable range; label tiers by audience in plain words, not abstract names; each higher tier opens with "everything in the previous tier, plus…" so readers scan only what is new; a differences-only toggle hides identical rows; mark each row's winner gently with shading plus a text or icon cue, never colour alone; do the arithmetic for the reader ("+$40/month buys 3 extra seats and single sign-on"); state the metric direction explicitly where ambiguous ("lower is better"); keep option labels and a decision row with one action per option sticky on long matrices; spell out annual savings next to the billing toggle; choose the container by difference count — cards when only a few real differences separate the options, tabs or accordions or a grouped collapsible matrix when the feature list is long |
| Permission request | Earn access without losing trust | Pre-permission rationale screen, system dialog, graceful denial path, settings route | Never request on first launch just in case; trigger when the person taps the feature that needs the access; stage one is a custom pre-permission screen stating the concrete value ("to scan receipts and auto-categorise expenses"); if the person taps "not now", do not fire the system dialog; stage two is the system dialog only after a positive pre-prompt response; request one permission at a time — batched prompts produce combined denials; on denial, degrade gracefully into a feature-limited experience, never a dead end; for permanent denial, explain the limitations plainly and route to the app settings; ask once, then only in context; never nag within the same session after a denial; consider a single in-app screen listing all requested permissions with one-tap revocation |
| Install prompt | Offer installation of a web app | Install action, benefit statement, dismiss action, manual-install instructions | Offer installation only after the person has used the app enough to see its value — after a completed task or a return visit — never on first load, never on exit, and never repeatedly after a dismissal; a dismissal stays dismissed, with a quiet persistent route (such as a menu entry) kept instead of re-prompting. State the concrete benefit beside the action (faster access, offline use, notifications) and keep one primary action, not a banner of options. Where the platform offers no prompt event, give manual steps instead of a dead button. After installation, confirm success and hide the prompt; the installed app opens in its own window without browser chrome where supported. Cross-check the permission request row |
| Search results | Recover from finding nothing | Query echo, carried filter chips, ordered recovery actions, facet panel | Keep the division of labour simple: search narrows by intent, filters narrow by attribute; the two controls sit close together since people loop between them; on empty results, say the combination matched nothing and echo it exactly ("no invoices match X with Status: Paid"), keep the query and filters visible, and never silently clear choices; offer recovery in order: a clickable spelling suggestion rather than silent autocorrect, a one-action scope broadening, carried filters as removable chips (an old filter is the most common hidden cause), and a create action where user content is accepted; label each widening action by what it changes; mirror applied filters as chips next to the query echo; a single reset clears filters but leaves the query intact; when applied chips overflow the available width, keep them in one horizontally scrollable row or collapse the excess into a single expandable chip showing how many are hidden, keep the reset control visible, and never reorder chips on selection — a chip stays in place so its position stays predictable; facet panels sit left on expanded screens and in a bottom sheet on compact ones, with live result counts per facet |
| Command palette | Run commands and jump to content by typing | Summon hint, query input, grouped result list, scope labels, shortcut hints | A complement to menus and buttons, never the only route to a command. Summon with one standard global shortcut; the input takes focus the moment the palette opens. Represent commands as data with verb-led names and match with forgiving subsequence matching plus synonyms, so a query in the user's words finds the right command. Group mixed results into typed sections — navigation, actions, destructive commands — so types stay distinguishable, and never truncate scope information ("Archive project" and "Archive selected files" must read differently after filtering). A blank palette shows recents and common actions; a no-match state explains and offers a next step, never a dead end. Keep selection stable while results stream in: state what happens when the query changes, and never execute whichever row occupies the first position at an uncertain instant. Do not let a broad fuzzy match outrank the clearly intended command when the consequence is costly. Full keyboard operation with a logical order, focus returned to the trigger on close, and result changes announced to assistive technology |
| Offline-first sync | Keep working without a connection | Local store, mutation queue, sync-status area, retry control, freshness indicator | The local store is the source of truth and the server converges later: mutations write to a durable queue with identifiers, timestamps, and attempt counts, and replay when connectivity returns, with a fallback where background sync is unavailable. The interface distinguishes granular states — syncing, local changes pending, stale — instead of a binary loading-versus-done split. Optimistic updates apply at once but stay marked pending until confirmed, then reconcile or roll back on rejection, never failing silently. A visible sync-status area carries the retry control and a manual refresh next to freshness indicators; failed sync gets a non-intrusive banner, never a modal. Derive the shown status from queue progress and real request outcomes, not from a connectivity signal alone: a device can reach a local network while the service itself stays unreachable. Optimistic display is for reversible edits only: where an action has lasting consequences — a booking, a payment, or an access change — keep it marked unconfirmed until the server confirms it, and never clear entered input until the local copy is durable |
| Offline download | Keep chosen content usable without a connection | Download action, size and storage statement, progress indicator, pause and resume controls, expiry statement, downloaded list, remove control | State the size and the storage the download will use before it starts, and refuse to start silently where the device lacks room — name how much room is needed. Show progress for each item with pause and resume that keep what was already fetched, never restarting from the beginning after an interruption. Where downloaded content expires, state the expiry before downloading and again in the downloaded list, and re-check it at the moment the content is opened rather than promising access the licence no longer allows. Removal frees the storage at once and says so, and a downloaded item that is no longer available states that plainly with a route to fetch it again. Distinct from the offline-first sync row, which queues changes made without a connection, and from the file upload row, which sends content rather than fetching it. ## Layout and responsive rules

- One pattern owns the primary action of a screen; supporting patterns stay visually quieter.
- On compact screens, patterns stack in task order: search, filters, results, actions.
- On expanded screens, filters may sit beside results; the result count stays with the results.
- Keep the path back: every pattern that opens a detail or a step offers a clear return.
- Do not nest dialogs; use a new view when a second layer of decisions appears.

## States

Every element and page in this group defines all seven states. Missing states are treated as incomplete work.

| State | Appearance | Behaviour |
| --- | --- | --- |
| Default | A pattern at rest, with full contrast and a clear label. | Ready for input or selection. |
| Hover | Pointer-only highlight: subtle background or border change. | No change on touch devices; hover never carries essential information alone. |
| Active | Pressed or selected appearance while interaction is in progress. | Feedback appears within 100 ms of input. |
| Disabled | Reduced contrast, no pointer response, still readable. | Explain why it is unavailable nearby when the reason is not obvious. |
| Loading | Skeleton blocks or a progress indicator replace live content. | Keep layout dimensions stable so content does not shift. |
| Empty | State why the area is empty and offer the action that fills it, or a reset when filters cause it. | Offer one clear next action and, where relevant, a reset for filters. |
| Error | Keep the pattern's structure, show the failure in place, and offer retry without losing input. | Keep entered data, place the message next to the problem, and offer a retry. |
